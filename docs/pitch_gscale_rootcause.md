# wz3 pitch 双峰分布的根因：估算虚高触发 `_pos_gscale` 压缩

> 2026-11-16 · captain 用 `PITCH_DBG` 实测 dump 锁定
> 关联 AGENTS #55 / #59

---

## 1. 现象：双峰分布

wz3 850 页的 pitch 误差（|out/src − 1|）分布：

| 百分位 | 误差 |
|---|---:|
| p50 | **0.7%**（一半的页几乎完美）|
| p75 | 2.8% |
| p90 | **14.5%** ← 尾部陡升 |
| p95 | 17.2% |
| >3% 的页 | **153 / 767 = 19.9%** |

**不是整体偏，是 20% 的页跳变。**

---

## 2. dump 实测（`PITCH_DBG=69,100,150`）

pass2（交付趟）的实际数值：

| 页 | 行数 | top_vs | strut_h | gap_h | total | cap | **gscale** | 结果 |
|---|---:|---:|---:|---:|---:|---:|---:|---|
| **p69** | 29 | 79.1 | 739.5 | 107.5 | **845.5** | 792.3 | **0.715** | ❌ 被压缩 28.5% |
| p100 | 25 | 73.1 | 637.5 | 70.5 | 762.3 | 792.3 | 1.000 | ✅ |
| p150 | 28 | 72.0 | 721.2 | 58.7 | 783.8 | 792.3 | 1.000 | ✅ |

**`USE_POS=True` 三页都一样，`PF=14.50` 一样，`sscale=1.000` 一样。**
**唯一的差别是 `gscale`：p69 被压到 0.715，另两页是 1.0。**

---

## 3. 根因：估算侧与渲染侧的 strut 公式不一致

| 侧 | 公式 | wz3 的值 |
|---|---|---:|
| **估算**（`_strut_h`，build_geom L1568） | `f['fnt'] * 1.34 * LINESPREAD` | **25.5pt/行** |
| **渲染**（`_strut`，L1643） | `bl - fnt*0.13`（行盒高），实际 advance ≈ `bl` | ~22.8pt/行 |
| **源书实测** | 墨迹行距 | **21.6pt/行** |

**估算比真实高 18%**（25.5 vs 21.6）。

对 p69（29 行）：
```
估算 strut_h = 29 × 25.5 = 739.5
真实内容     = 29 × 21.6 = 626.4
虚高         = 113.1pt   ← 把 total 从 732.4 推到 845.5，越过 cap 792.3
```

**于是 `_pos_gscale = (white − need)/white = (186.6 − 53.2)/186.6 = 0.715`**
→ `top_vs` 和 `gap_h` 被压 28.5% → 布局变形 → pitch 错。

---

## 4. 为什么是「双峰」而不是整体偏

`total` 与行数近似成正比：

```
行数 × 25.5 + top_vs + gap_h  >  cap(792.3)?
```

- **行数少**（≤约 28 行）→ `total` 不超 cap → `gscale = 1` → 按源 y 正确落位 → pitch 误差 <3%
- **行数多**（≥29 行）→ 超 cap → 强制压缩 → pitch 误差 10~18%

**所以失败页 = 行数超过阈值的页** —— 这正好对应诊断（t345）里
「书眉短页 85 + 章标题页 73」：这些页在同样版心内塞了更多行。

---

## 5. 修法（两处，需一起核对）

### ① 估算侧对齐真实行距（主因）
`build_geom.py` L1568：
```python
_strut_h += round(f['fnt'] * 1.34 * LINESPREAD, 1)      # 25.5，虚高 18%
```
应改为与渲染侧一致的口径（`bl` 或该页源图实测行距）：
```python
_strut_h += round(bl, 1)                                 # ≈22.8
```

### ② cap 偏紧（次要）
即便用真实行距，p69 的 `total = 79.1 + 626.4 + 107.5 = 813.0` 仍略超 `cap 792.3`
（+21pt / +2.6%）。需核对 `_cap = _TEXTH * POS_FILL` 的 `_TEXTH` 口径：
`cap 792.3` 反推 `_TEXTH = 733.6`，而 wz3 实际页高 872.7 → 版心可用高度可能被低估。

## 6. 为什么之前 6 次修都无效

| 尝试 | 为什么没用 |
|---|---|
| t346 剔除注文行（verify 侧） | 改的是**度量**，不是压缩触发条件 |
| t347 页码当页边 | 只解释 wz2 的一部分 |
| t349 书眉按源 y | 书眉不影响 `total`，压缩照旧 |
| t353 首块按源 y | 同上，被 `gscale` 压回去 |
| t354 改 `bl`（渲染侧 strut） | **改错了侧** —— 压缩由估算侧的 `_strut_h` 决定，渲染侧改了也不影响判定 |

**t354 的关键失误**：`bl` 是渲染用的，而 `_pos_gscale` 的触发只看 `_strut_h`（估算）。
两侧公式不一致，改一侧不解决另一侧。
