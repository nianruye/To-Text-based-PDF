## 我做了什么、错在哪

基于 `count_open.py` 的统计（冒号列左邻列首缺 `﹁`），我认定有 134 处高置信度缺失，

（16 处被源图墨迹闸门拦下，全是诗句首字的真「一」）。


## 根因：拿 OCR 数据当产物

逐位置对照 v25 与 v26 的产物文本：

```
p87   正是：   v25 '：﹁說'    v26 '：﹁說'     ← 完全一样
p92   為證：   v25 '：﹁壯'    v26 '：﹁壯'
p99   但見：   v25 '：﹁萬'    v26 '：﹁萬'
p120  為證：   v25 '：﹁兩'    v26 '：﹁兩'
p135  為證：   v25 '：﹁一'    v26 '：﹁一'
```

**v25 的产物里 ﹁ 本来就在。** 渲染端 §1.998 的 QSF（issue #33 引号形状修复）
按**源图墨迹形状**（四角不对称度 + 开闭方向 `bias=(c1+c2)-(c3+c4)`）判定，
已经把列首的 `一` 渲染成 `﹁`。

`count_open.py` 数的是 `data/.../lines_patched.json` 里**OCR 文本**的字符，
而产物是**墨迹驱动重排后**的结果。两者不是一回事。

**「冒号后缺开引号」这个问题在产物里不存在，是统计口径造成的假象。**

## 教训（已写进技能库）

**「缺某个符号」的规模必须数产物，不能数 OCR 数据。**
渲染端有多处**墨迹驱动的符号修复**（QSF 的 `一 → ﹁/﹂`、R2 破折号、段首圈点），
OCR 数据里「少」的东西，产物里可能已经有了。

正确顺序：

```
① 在产物 PDF 上数「缺多少」           <- 这才是用户看到的
② 只有产物真缺，才去数据层找原因
③ 数据层改了以后，用产物上的同一个量验收
```

我在第 ① 步就跳过了产物，直接按数据层的统计动手 —— 和这一轮此前的 5 次判据失误同一个成因：
**没有先确认判据所依赖的量到底是什么。**
