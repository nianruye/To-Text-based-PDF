# /opt/test 生成-验证-修正飞轮行动卡

> 用在：把单次 AI 编码升级成可持续的工程流程。目标是让 AI 产出每次都经过可复现验证，再由人裁决。本项目有三条管线、两种校准、四类文档——飞轮让它们不散架。

## 输入

- 任务或 issue（来自 05 卡分类后的待完成列表）
- spec / 规则文件（`spec/` + `docs/AGENTS.md`）
- 测试和 CI（`test_cases.py` + `verify_geom.py` + `.github/workflows/ci.yml`）
- PR 审查流程（`git diff` + 人审）

## 本项目的飞轮定义

```
┌─────────────────────────────────────────────────────────┐
│                     /opt/test 质量飞轮                     │
│                                                         │
│  AI 生成代码                                              │
│    │                                                    │
│    ▼                                                    │
│  ruff lint ───────────── 红 → 结构化失败信息回喂 AI       │
│    │ 绿                                                  │
│    ▼                                                    │
│  test_cases.py (≥33条) ── 红 → 按"失败项/输入/期望/实际"  │
│    │ 绿                      格式分析，回喂 AI            │
│    ▼                                                    │
│  verify_geom.py ──────── 红 → 量化为指标变化(如 pitch     │
│    │ 绿                      从95.3%降到80%)，回喂 AI      │
│    ▼                                                    │
│  PR diff < 200 行 ──── 太大 → 要求拆小，重新来            │
│    │ diff 合理                                           │
│    ▼                                                    │
│  人审 spec 对账 + 行为不变确认                             │
│    │                                                    │
│    ▼                                                    │
│  人按 merge                                              │
└─────────────────────────────────────────────────────────┘
```

## AI 动作（每个任务循环）

### 1. 生成：按 spec 或 issue 做最小实现

- 先读对应 spec（如 `spec/ancient/01_pitch_overlap.md`）和规则文件（`docs/AGENTS.md`）
- 给出最小实现计划，等用户确认后再改代码
- diff 每次控制在 200 行以内（新增 + 删除）
- commit 信息格式：`feat(scope): 描述\n\nRefs #N`

### 2. 验证：运行三层检查

**第一层：ruff lint（10 秒）**
```bash
ruff check src/
```
- 红 → 查看失败行 → 最小修复 → 重新 lint
- 常见翻车：未使用的 import、未定义的变量、裸 except

**第二层：test_cases.py（30 秒）**
```bash
python3 src/test/test_cases.py output/基线_wz2_classic.pdf
```
- 红 → 按结构化格式分析：
  ```
  失败项: test_pitch_p11
  输入: output/基线_wz2_classic.pdf
  期望: pitch 33-37
  实际: pitch=42.1
  原因分析: 改了 build_classic.py:L150 的 pitch 计算 → 行距变大
  最小修复: 回退 L150 的改动 OR 确认这是有意的行为变化
  ```
- 不要跳过分析直接让 AI 改——先理解为什么红

**第三层：verify_geom.py（按需 2-10 分钟）**
```bash
python3 src/test/verify_geom.py output/out.pdf \
  data/wz2/wz2_spotting_coords.json data/wz2/wz2_spotting_lines.json \
  --src-pdf source_pdf/wz2.pdf --json /tmp/verify.json
```
- 只在 PR 合并前或 scheduled CI 跑（不阻塞每个 commit）
- 红 → 量化为指标变化：pitch 从 59.1% → X%、溢出从 0 → Y 页、空白页从 97 → Z
- 如果指标变差，视同测试失败，必须修复

### 3. 修正：根据结构化失败信息做最小修改

- 只根据失败信息修改导致失败的那部分代码，不要扩大 scope
- 修正后重新跑全部三层验证
- 如果同一处改三次还红，停下来问人

### 4. 记录：在 PR 里写清验证结果

PR 模板：
```markdown
## 改动范围
- 修改了 build_classic.py:L150 pitch 计算逻辑
- 新增 src/utils/tex_escape.py 共享模块

## 验证结果
- [x] ruff check src/ — PASS
- [x] test_cases.py (25条) — 25 PASS 0 FAIL
- [ ] verify_geom.py — 跳过 (非 PR 阻塞，scheduled 会跑)

## 未改动范围
- 环境变量约定不变
- 命令行参数不变
- build_geom.py 不受影响

## 风险
- wz2 附录标题页（p580-600）的 pitch 可能轻微变化，需人工确认
```

## 人审动作（在飞轮的每个节点）

| 环节 | 人审什么 |
|------|---------|
| **生成前** | spec 是否正确？issue 边界是否清楚？ |
| **lint 红时** | AI 的修复是否最小？有没有因 lint 修复引入逻辑变化？ |
| **测试红时** | 先判断：是测试写错了、行为真的变了、还是状态没隔离？不只看 AI 的解释 |
| **verify_geom 红时** | 指标变化是否可接受？如果 pitch 从 59.1% 降到 58%，是噪音还是真回归？ |
| **PR diff** | diff 是否 < 200 行？是否只做了一件事？有没有顺手修 bug？ |
| **merge 前** | spec 是否同步更新？测试是否全绿？verify_geom 是否无回归？ |

## 本项目的特殊验证点

除了 lint + pytest，PDF 排版系统还需要额外的验证：

| 验证项 | 为什么重要 | 怎么验证 |
|--------|----------|---------|
| **输出 PDF 可被 fitz 打开** | xelatex 编译成功 ≠ PDF 合法 | `fitz.open(out_pdf)` 不抛异常 |
| **页数不增加** | 「溢出」是最严重的回归 | `assert len(pdf) == src_pages` |
| **全文无乱码字符** | OCR + LaTeX 转义可能引入 | `grep -r '￿\|\\textbackslash' output.tex` |
| **全部 spec 测试点有覆盖** | 防功能级回归 | 05 卡的 spec↔test 映射表 |
| **命令行参数向后兼容** | 下游脚本可能依赖当前约定 | 用旧参数跑一遍，输出能打开即可 |

## 完成标准

- 每个 PR 都有 ruff + test_cases 的验证结果记录在 PR 正文里
- 失败信息结构化回喂（按「失败项 / 输入 / 期望 / 实际 / 最小修复」格式），不是只说「有 bug」
- 人只在标准定义、语义判断、合并决策上做最终裁决——不帮 AI 看 lint 错误
- 流程能被团队重复执行——新成员能按这份卡独立完成一轮飞轮

## 禁止事项

- 禁止用「AI 说已经完成」当完成标准——以 CI 绿灯和特征测试全绿为准
- 禁止没有验证就进入下一步——生成完不跑 lint 就直接 commit 是本项目最大的质量债
- 禁止失败信息不结构化——只能说「测试挂了」是无用的，必须分析到具体断言和原因
- 禁止把一次成功当成长期可信——wz2 每次 run 之间 pitch 可能有 ±0.3% 的 xelatex 浮动，这是正常的，不要因此过度优化
- 禁止跳过三层验证的任何一层——lint 挡住格式问题，test_cases 挡住行为回归，verify_geom 挡住整体漂移
- 禁止 AI review 替代确定性检查——GitHub Copilot review 可以说「建议检查这里」，但不能决定能不能 merge

## 可复制 Prompt

```text
请按生成-验证-修正流程执行本任务。这是 /opt/test PDF 排版还原系统。

项目约束：
  - 三条渲染管线：build_classic.py (复杂注释排版)、build_geom.py (现代)、build_pdf_v13.py (旧)
  - 验证三层：ruff check src/ → test_cases.py → verify_geom.py
  - diff 每次 < 200 行
  - 重构和修 bug 必须分 PR

本任务流程：
1. 先列出本任务的验证标准（基于对应 spec 的测试点）
2. 做最小实现（先给计划，等我确认后再改代码）
3. 运行 ruff check src/，贴出关键结果
4. 运行 test_cases.py，贴出 PASS/FAIL 统计
5. 如果失败，请按以下格式分析：
   ```
   失败项: <测试名>
   输入: <基线 PDF 路径>
   期望: <原始断言>
   实际: <实际值>
   原因分析: <行为变化原因>
   最小修复: <修复方案>
   ```
6. 修复后重新运行验证
7. （可选，大改动时）运行 verify_geom.py 并对比指标变化
8. 最后输出：
   - 改动范围（哪些文件、哪些函数）
   - 验证结果（lint/test/verify 三项状态）
   - 剩余风险（哪些边界情况未覆盖）
   - 需要人裁决的问题（如 pitch 轻微变化是否可接受）

不要跳过验证，不要把未验证内容说成已完成。
如果 AI 连续 3 次修复仍不能全绿，停下来向人报告具体阻塞点。
```
