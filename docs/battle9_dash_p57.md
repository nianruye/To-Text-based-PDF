### 1.3 与 t34 dash rule 四道比值判据对照

step 取 spec §15 的 p57 实测值 **63.72pt**；插入 `——` 时组内字符数 **nd=2**。

| 判据 | 公式 | 实测 | 阈值 | 结论 |
|---|---|---|---|---|
| **线长** | len / (step×nd) | 79.5 / 127.44 = **0.624** | 0.45–1.70 | ✅ 通过 |
| 线长（参考比值） | len / step | 79.5 / 63.72 = **1.248** | ≈DASH_LEN_RATIO 1.26 | ✅ 一致 |
| **线位** | 线段落在本组格区内比例 | **≈1.0**（线段整体位于 `書` 与 `導` 之间的本组两格区内） | ≥0.75 | ✅ 通过 |
| **线心** | \|xc−列心\| / step | 0.55 / 63.72 = **0.0086** | ≤0.25 | ✅ 通过 |
| **线宽** | width / step | 5.25 / 63.72 = **0.0824** | ≤0.35 | ✅ 通过 |

→ 四项全过；且该线段**不是字笔画**：孤立（上下均有 5–6pt 间隙）、宽 5.25pt 远小于标题笔画、线心与列心对齐、沿 y 连续无断。

## 3. 落库方案与风险（只给方案，本轮不实施）

### 3.1 p57 破折号（推荐 Plan A：数据-only）

**方案 A（推荐）**：在 fix JSON 增加一条 `missing_char`：
```json
{"class":"missing_char","page":57,"col":[792.0,247.2,866.7,955.6],"pos":7,"ch":"——",
 "side":"","source":"punct_list","confidence":"high","text":"論金瓶梅這部書導讀"}
```
- 构建时 `_apply_missed_fix` 在标题列文本 pos=7（`書` 后）插入 2 个 `—`；
  `_dash_runs` 要求「文本相邻 + 格号连续」，两个 `—` 会被并成一组；
  `_dash_ink_seg` 在本组格区实测源墨 → 画**一条** `\rule`（高度 79.5–80.25pt、线心 829.9），文本层 `——` 用 `3 Tr` 不可见（可搜索），字符量 +2。
- 与现有 `class=dash` 的区别：`class=dash` 目前只支持**行首前置** `DASH_INS`（`sl[k][idx] = DASH_INS*n + sl[k][idx]`），而 p57 的破折号在**列中**（`書` 与 `導` 之间）——直接用它会把线画到列首，不可用。

**落库后验证项（test build，本轮不做）**：
1. 只有**一条**竖线（非两条），y0/y1 与源图 736.5/816.75 差 ≤0.25pt，x 中心 829.9；
2. 线长/step ≈1.25，线宽按 `VERT_DASH_RULE_W`（默认 2.78pt；源图 5.25pt，可用 `='src'`）；
3. 文本层 `——` 可搜索、`verify_vert` 字符量 931,178→931,180（+2）；wz6 不受影响；
4. 标题列版式：插入 2 字符后标题字符可能重新均摊（spec §8 已记录产物标题字位与源书有差），需目检 `書`/`導` 是否被压/错位。

**风险**：
- 标题行（§1.995 标题/署名路径）是否走 `col_puts`/`_dash_runs`：spec §15 的 p57 测试产物已验证过（80.25pt/1.259 step），但**当前构建数据的标题列没有 `——`**，需先 test build 确认该路径仍生效；
- 若标题路径把 `——` 按两个字形画出（未走 rule），用户看到的仍是「两条竖线」，本方案无效；
- t27 的 `cell` 是错的（见 §4），落库必须用 `pos=7`，不能用 t27 cell/crop；
- 字符量 +2 会让 verify 的字符量与 v37 不同（属预期，不是回归）。

**方案 B（代码改动，不推荐）**：给 `class=dash` 增加 `pos` 字段（把 `DASH_INS*n` 插到列中而非行首）——文本层不新增 `——`，但需改 `build_vert`，并重跑全量；本轮 out-of-scope。

### 3.2 p186 `」。`（可落库）

- `missing_char ch='」。' pos=2`（page 186，col [143.2,217.0,174.6,1345.0]）；2 字符插入到 `餓鬼` 后。
- 风险：① 2 字符字符串插入一个 pos，渲染端按 2 格排；需 test build 确认不被拆错；② `﹂` 与更早的开引号跨列配对，punct_audit 行级口径可能报 B（源墨已证在），属审计口径问题；③ 字符量 +2。

### 3.3 p147 `，`（不建议只落逗号）

- 源图 `！﹂，那`；若落库应 `ch='」，'`（2 字符）而非 `，`；或按 QSF/引号机制处理 `﹂`。
- 风险：`！」，` 的标点顺序不常见，需与源书/GB/T 复核；`﹂` 与更早开引号跨列配对，审计可能报 B/K；字符量 +2。
- 若只想要「逗号」这一层，t27 的 `，` 是真，但会留下 `﹂` 缺失——不建议。

### 3.4 p1330 `，`（不落库）

- 无逗号墨迹（仅噪点），t27 该条误报；不落库、不改数据。

## 4. t27 座标问题（p57 特别说明）

- t27 条目 `cell=[792.0,424.3,866.7,449.6]`，但 p57 实际破折号墨段在 **y 736.5–816.0**；cell 落在 `部/書` 区（见 `p57_annot.png` 红框与 `p57_t27cell_10x.png`）。
- t27 的 `crop=tmp_vert/battle6/all_insert_crops/00037.png`（96×96）显示的是大字笔画，**不是破折号**；`strip`（264×2564）才是整列。
- 因此：p57 的 API 判定「有破折号」**结论正确**，但 `cell/crop` 证据**错位**（标题行坐标按字符均摊计算，与实际大字位置不符）；落库时以 `page/col/pos/text` 为准（pos=7），不要用 cell。
- p147/p186/p1330 的 cell 基本落在目标墨迹上（p147 含角形+逗号；p186 含角形；p1330 含噪点），错位问题主要在 p57 的大字标题行。
